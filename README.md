# E-commerce SQL Analysis

## О проекте

SQL-проект по анализу транзакционных данных интернет-магазина на основе датасета **Online Retail**.

Данный проект является **SQL-версией ранее выполненного проекта по анализу того же набора данных в Python**. Основная цель переноса — воспроизвести аналитический процесс средствами **MySQL 8+** и продемонстрировать применение SQL для решения практических задач Data Analyst.

Проект имитирует работу Data Analyst в e-commerce компании: от загрузки и проверки исходных данных до анализа продаж, клиентов, товарного ассортимента, возвратов, RFM-сегментации и удержания клиентов.

---

## Цели проекта

В рамках проекта рассматриваются следующие направления:

* анализ динамики продаж и выручки;
* оценка количества заказов и среднего чека;
* анализ географии продаж;
* исследование покупательской активности в течение дня;
* анализ товарного ассортимента;
* оценка концентрации выручки среди клиентов;
* анализ частоты покупок;
* исследование возвратов и отмен;
* RFM-сегментация клиентов;
* когортный анализ и оценка удержания клиентов.

## Данные

В проекте используется оригинальный датасет **Online Retail**, содержащий транзакции интернет-магазина за период с декабря 2010 года по декабрь 2011 года.

Исходный набор данных содержит **541 909 строк** и следующие поля:

| Поле          | Описание              |
| ------------- | --------------------- |
| `InvoiceNo`   | Номер заказа          |
| `StockCode`   | Код товара            |
| `Description` | Описание товара       |
| `Quantity`    | Количество товара     |
| `InvoiceDate` | Дата и время операции |
| `UnitPrice`   | Цена единицы товара   |
| `CustomerID`  | Идентификатор клиента |
| `Country`     | Страна                |

Исходный файл не включён в репозиторий. Информация о получении и подготовке данных находится в [`data/README.md`](data/README.md).

## Этапы анализа

### 1. Настройка базы данных

`01_database_setup.sql`

Создаётся база данных `ecommerce_analysis` и таблицы для хранения исходных и импортируемых данных.

Используются две таблицы:

* `online_retail_import` — промежуточная таблица для загрузки CSV;
* `online_retail_raw` — таблица исходных данных после преобразования типов.

---

### 2. Загрузка данных

`02_data_import.sql`

Исходный CSV загружается в промежуточную таблицу с помощью `LOAD DATA LOCAL INFILE`.

После загрузки выполняется преобразование:

* количества товаров в числовой формат;
* даты и времени в `DATETIME`;
* цены в числовой формат;
* пустых значений `CustomerID` в `NULL`;
* очистка символов конца строки в поле `Country`.

---

### 3. Проверка данных

`03_data_inspection.sql`

Проводится первичная проверка качества данных:

* размер набора данных;
* временной период;
* количество уникальных заказов, товаров, клиентов и стран;
* пропущенные значения;
* отрицательные и нулевые значения;
* отменённые заказы;
* экстремальные значения;
* полные дубликаты;
* отрицательные цены.

Этот этап позволяет определить проблемы исходных данных до применения правил очистки.

---

### 4. Очистка данных

`04_data_cleaning.sql`

Для основного анализа продаж формируется отдельная таблица `online_retail_clean`.

В неё попадают только операции, удовлетворяющие условиям:

```sql
Quantity > 0
AND UnitPrice > 0
```

Таким образом, из основного набора исключаются отрицательные количества, нулевые и отрицательные цены.

Исходная таблица `online_retail_raw` сохраняется без изменений и используется для отдельного анализа возвратов и отмен.

Полные дубликаты на данном этапе автоматически не удаляются, поскольку их наличие требует отдельного методологического решения.

---

### 5. Создание аналитических признаков

`05_feature_engineering.sql`

На основе `InvoiceDate` создаются дополнительные признаки:

* дата;
* год;
* месяц;
* день недели;
* час;
* месяц в формате `YYYY-MM-01`.

Также рассчитывается выручка:

```text
Revenue = Quantity × UnitPrice
```

Выручка используется как основной финансовый показатель анализа.

Она не является прибылью, поскольку в исходных данных отсутствуют себестоимость товаров, маркетинговые расходы и другие операционные затраты.

---

### 6. Исследовательский анализ

`06_eda.sql`

Рассматриваются:

* общая выручка;
* количество заказов;
* количество клиентов;
* средний чек;
* месячная динамика продаж;
* изменение показателей относительно предыдущего месяца;
* распределение выручки по заказам;
* география продаж;
* продажи по часам;
* наиболее продаваемые товары;
* товары-лидеры по выручке и количеству проданных единиц.

Для анализа динамики используются оконные функции, в том числе `LAG()`.

---

### 7. Анализ клиентов

`07_customer_analysis.sql`

Для клиентов с известным `CustomerID` рассчитываются:

* общая выручка;
* количество заказов;
* количество приобретённых товаров;
* средний чек;
* накопленная выручка;
* доля выручки;
* частота покупок.

Отдельно анализируются:

* концентрация выручки среди наиболее крупных клиентов;
* разовые и повторные покупатели;
* распределение клиентов по количеству заказов;
* возвраты;
* количество клиентов, совершавших возвраты;
* распределение количества возвратов и возвращённых единиц.

---

### 8. RFM-анализ

`08_rfm_analysis.sql`

Клиенты сегментируются по трём характеристикам:

* **Recency** — давность последней покупки;
* **Frequency** — количество заказов;
* **Monetary** — общая выручка клиента.

Для каждой метрики формируется оценка от 1 до 5 с использованием оконной функции `NTILE()`.

На основе полученных оценок формируются клиентские сегменты.

Результатом является таблица с:

* RFM-метриками;
* оценками `R`, `F`, `M`;
* суммарной RFM-оценкой;
* сегментом клиента.

---

### 9. Когортный анализ

`09_cohort_analysis.sql`

Клиенты объединяются в когорты по месяцу первой покупки.

Для каждой когорты рассчитывается:

* количество клиентов;
* активность клиентов в последующие месяцы;
* доля клиентов, совершивших повторную покупку.

Формируется когортная матрица удержания, где:

* строки — месяцы первой покупки;
* столбцы — месяцы относительно первой покупки;
* значения — доля клиентов когорты, совершивших покупку в соответствующий месяц.

---

# Основные выводы и рекомендации

### Продажи и география

Основная часть выручки приходится на Великобританию — около **84,6%**.

При этом осенью наблюдается заметный рост продаж, особенно в период **сентябрь–ноябрь 2011 года**.

### Концентрация выручки

Выручка сильно сконцентрирована среди клиентов: **20% клиентов формируют около 74,6% клиентской выручки**.

Это показывает высокую зависимость общего объёма выручки от относительно небольшой части клиентской базы.

### Повторные покупки

Повторные клиенты составляют **65,6% клиентской базы**, но обеспечивают **93,1% выручки** среди клиентов с известным идентификатором.

Таким образом, основное различие между разовыми и повторными покупателями связано прежде всего с частотой совершения заказов.

### Удержание клиентов

По результатам когортного анализа видно, что наиболее заметное снижение удержания клиентов происходит уже в первые месяцы после первой покупки.

В большинстве когорт через месяц после первой покупки возвращается около **15–24% клиентов**.

В дальнейшем доля возвращающихся клиентов в основном находится в диапазоне **20–30%**, хотя заметно меняется от месяца к месяцу. У некоторых когорт наблюдается более высокая активность в отдельные периоды, например у клиентов, впервые совершивших покупку в июне и сентябре 2011 года.

Последние когорты пока нельзя полноценно сравнивать с ранними, поскольку для них доступно меньше месяцев наблюдения.

В целом основной потенциал для роста связан с увеличением доли клиентов, которые совершают повторную покупку после первой.

## Рекомендации

На основе проведённого анализа можно выделить несколько направлений для дальнейшей работы:

* уделить особое внимание ключевым и лояльным клиентам, которые формируют значительную часть выручки;
* отдельно работать с ценными клиентами, снизившими активность, поскольку их возврат потенциально может иметь больший эффект, чем работа с менее ценными клиентами;
* разработать механики, стимулирующие повторную покупку после первого заказа, так как именно на этом этапе наблюдается наиболее заметное снижение активности.

## Ограничения анализа

При интерпретации результатов необходимо учитывать ограничения исходных данных:

1. Для значительной части транзакций отсутствует `CustomerID`, поэтому они не могут использоваться для анализа индивидуального поведения клиентов.

2. Для основного анализа продаж используется фильтр:

```sql
Quantity > 0
AND UnitPrice > 0
```

При этом исходная таблица сохраняется для отдельного анализа возвратов и отмен.

3. В данных отсутствует информация о себестоимости и расходах. Поэтому по имеющимся данным невозможно корректно рассчитать прибыль, маржинальность, CAC и полный LTV.

4. Данные заканчиваются 9 декабря 2011 года, поэтому последний месяц наблюдения является неполным.

5. RFM-сегментация зависит от выбранного метода формирования групп и правил сегментации. Полученные сегменты являются аналитической моделью.

6. Когортный анализ основан на факте совершения покупки и не учитывает причины изменения клиентской активности.

## Как запустить проект

### 1. Установить MySQL 8+

Для работы с проектом требуется MySQL 8 или более новая версия.

### 2. Получить исходный датасет

Скачать `Online Retail.xlsx` и подготовить CSV согласно инструкции в [`data/README.md`](data/README.md).

### 3. Создать базу данных

Выполнить:

```text
sql/01_database_setup.sql
```

### 4. Загрузить данные

Указать путь к CSV-файлу в:

```text
sql/02_data_import.sql
```

и выполнить файл.

### 5. Выполнить SQL-файлы последовательно

```text
03_data_inspection.sql
04_data_cleaning.sql
05_feature_engineering.sql
06_eda.sql
07_customer_analysis.sql
08_rfm_analysis.sql
09_cohort_analysis.sql
```

Каждый следующий этап использует результаты предыдущего.
